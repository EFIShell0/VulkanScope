# VulkanScope 0.33.3 Full Application Audit

Audit scope: Kotlin/Compose lifecycle and reporting, isolated probe service ownership, JNI/native Vulkan safety bounds, TXT/HTML/schema-v3 parity, Database 0.35.3 submission compatibility, update/network paths, build metadata, and current upstream specification claims.

Concrete fixes:
- Released the service-side parcelled Surface deterministically after every isolated probe task.
- Prevented unchanged base-probe checkpoints from being repeatedly re-read and reparsed while waiting for the next atomic publication.
- Corrected Android wide-gamut false-state presentation from unavailable/not-exposed wording to Unsupported.
- Preserved the Database 0.35.3 rule that an empty reported HDR type list is Unavailable rather than inferred Unsupported, and made that state explicit in structured JSON.
- Added additive `hdrCapabilityStatus` and `preferredWideGamutColorSpace` structured display fields while retaining Database 0.35.3 legacy keys.
- Corrected the dormant base surface present-mode safety comparison to use `kMaxPresentModeEntries`.
- Updated upstream-source wording: published Khronos Vulkan is 1.4.358 as of 2026-08-20; project producer/query staging baseline remains independently pinned/validated at 1.4.360.

Turnip/SAF internals were intentionally not changed.

## HDR luminance sentinel correctness

- Android defines `Display.HdrCapabilities.INVALID_LUMINANCE` as the invalid sentinel. VulkanScope must not treat a valid finite `0.0` luminance value as automatically not exposed.
- HTML Surface diagnostic booleans such as second-query-attempted, safety-rejected, and extension-enabled are scalar diagnostic values, not support-state booleans; they must render as literal values rather than Supported/Unsupported badges.

## API-level display-state correctness

- `Display.isWideColorGamut` is available from API 26. On API 24-25 VulkanScope reports the state as Unavailable rather than converting the unavailable query into Unsupported.

## Probe checkpoint race hardening

- Length/mtime change detection avoids hot-loop JSON parsing, while a bounded periodic refresh prevents a rapid atomic replacement with identical length/timestamp metadata from being missed until timeout.
