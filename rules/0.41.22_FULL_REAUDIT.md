# VulkanScope 0.41.22 full re-audit

## Scope

This audit rechecks VulkanScope 0.41.21 against `rules/PROJECT_RULES.md` for canonical Vulkan naming, query/result semantics, report preservation, Vulkan 1.4.360 compatibility, Android display evidence, multi-device usability, Turnip/archive safety, isolated-probe path confinement, native/JNI ownership, performance bounds and package hygiene.

## Corrected evidence semantics

- A successful Android HDR-type query with zero returned types is completed zero-result evidence, not an unavailable query. UI, TXT and HTML use one state-aware formatter so Available-empty, Unknown and Unavailable cannot diverge between report surfaces.
- Vulkan API gates use major+minor comparison for versioned features/properties; minor-only capability gates outside canonical version helpers are rejected.
- Vulkan Video format and Vulkan Tool enumerations distinguish completed zero results, bounded partial `VK_INCOMPLETE` evidence and query failure.
- Device-layer absence, Turnip eligibility and Surface presentation remain state-aware rather than collapsing Unknown/Incomplete into negative capability claims.
- Every distinct current `VkResult` value in the pinned Vulkan 1.4.360 header has a canonical presentation name; unknown future numeric values remain explicit raw unknown evidence. Image Format Properties2 structured outcomes retain raw numeric and canonical text together.

## Multi-device usability and report parity

All runtime-enumerated physical devices are selectable for device-specific application pages. Complete TXT/HTML/technical reports continue to preserve the full device set. Multi-device filenames and TXT/HTML summary cards do not imply that the first GPU represents the entire report.

## Security and resource hardening

Turnip ZIP extraction rejects duplicate canonical archive paths in addition to traversal and size/count violations. The isolated probe service passes the validated cache-confined canonical result path to native/result publication. Existing HTTPS/no-cleartext, update package/signing validation, Database no-redirect/all-or-nothing bounds, JNI string release, `ANativeWindow` release and Vulkan object cleanup requirements remain in force.

## Validation boundaries

`tools/verify_release.py`, checked-in JSON/XML parsing and Python tool syntax are run locally. Header/registry auxiliary generators that require a separately materialized authoritative `vulkan_core.h` or `vk.xml` are not claimed as rerun when those external source files are unavailable in the audit container. The checked-in generated artifacts remain gated by the release verifier and pinned commit metadata.

A full Android release build is attempted separately. If the Gradle wrapper cannot obtain its pinned distribution because of the audit environment, that is recorded as an environment limitation rather than reported as a successful build.

The final source ZIP is re-extracted into a clean directory and the package itself is revalidated before release.
