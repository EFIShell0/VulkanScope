# VulkanScope 2.0.1 session-based isolated collection audit

## Release scope
- Version: 2.0.1.
- versionCode: 2001.
- Functional predecessor: VulkanScope 2.0.0.
- Purpose: remove the measured process-per-query orchestration bottleneck without weakening isolation, evidence semantics, bounded execution or report completeness.

## Measured cause addressed
- The 2.0.0 device evidence showed complete collection at 15,913 ms, base collection at 134 ms, metadata + Surface at 223 ms and background details at 15,555 ms across 125 dedicated probes.
- The optimized path therefore targets repeated process launch / service handoff / host polling overhead in background details rather than changing Vulkan support semantics or dropping queries.

## Architecture
- Base, metadata, Surface and user-triggered ad-hoc queries keep the established one-shot dedicated-process path.
- Automatic background-detail collection partitions the same ordered core, advanced and validated extension query groups into isolated `:vulkan_probe` service sessions of at most 16 groups each.
- Each session loads `libvulkanscope` once and invokes the existing JNI query entry point sequentially for at most 16 groups before process teardown, bounding process-owned Vulkan resources while removing most process/bootstrap handoffs.
- Every group still has an independent result file, service-owned terminal marker, timing sidecar and original 12 s or 30 s per-group hard deadline.
- The complete sequence of background sessions remains subject to the existing 60 s host budget.

## Crash and timeout recovery
- The native crash guard remains installed per query and remains pointed at that query's dedicated result path.
- A native signal or per-group hard timeout terminates only the isolated probe process, never the app process.
- Completed groups are consumed and retained as validated evidence while the session is running so session cache growth stays bounded.
- If a group crashes or times out, a valid atomic terminal candidate is retained when available; otherwise that exact group becomes explicit unavailable with a factual reason.
- Unexecuted groups after a crashed/terminated session are resumed in a fresh isolated session process while the overall 60 s budget remains available.
- Missing results are never converted to unsupported.

## Security and resource bounds
- Session group count is bounded to 16 per isolated process session.
- Group names are nonblank, at most 256 characters and reject NUL input.
- Per-group timeouts remain bounded to 1,000..60,000 ms and are supplied one-for-one with session groups.
- The session directory is canonicalized and must remain inside private `cacheDir`; all result, terminal, timing, started, timeout and crash paths are derived from numeric indexes inside that validated directory.
- Individual result size remains capped at 64 MiB and timing sidecars remain capped at 16 KiB.
- Completed group files are read, validated and deleted while the service continues with later groups.
- Session cancellation forces confirmed dedicated-process quiescence and private session-directory cleanup.

## Correctness boundaries
- Query selection, validated extension coverage, query ordering, 1.4.364 registry/header lock, native query implementation, capability-state semantics, report/Database schemas, permissions and network policy remain unchanged from 2.0.0.
- Core/advanced/extension data is still merged through the same existing merge functions after strict terminal JSON validation.
- Existing one-shot publication, terminal ownership, timeout and cancellation paths remain intact for base, metadata, Surface and ad-hoc collection.

## Performance evidence
- `Analysis -> Collection diagnostics` retains the 2.0.0 timing evidence and adds `Background process launches` and `Session host time`.
- Normal successful background collection should require a small bounded number of isolated background process launches instead of one process per query group.
- Exact device-side speedup is not asserted until measured on hardware after installation.
