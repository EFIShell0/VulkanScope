# VulkanScope 0.41.12 Database submission reliability audit

## Faults found in 0.41.11

- The complete-report UI gate accepted any device-bearing snapshot once `CollectionStatus` was not `COLLECTING`, even if the top-level `VulkanReport.error` was non-null. The deployed Database contract requires `collection.error` to be null, so such a snapshot was presented as submittable even though the Worker must reject it.
- Database JSON/report serialization occurred before the submission `runCatching` boundary. A local payload-construction exception could therefore escape the suspend function. The Info-page coroutine also reset `submissionInFlight` only after a normal return, so an escaping exception could leave the action stuck in `Submitting…`.

## Corrections

- The shared complete-report gate now requires a physical-device report, null top-level report error, and no active collection. TXT, HTML, Database submission and the existing collection-protected driver actions use the same gate.
- `submitDatabaseReport` performs a second fail-closed report-completeness check immediately before payload generation.
- Complete payload serialization is guarded and reports a local serialization failure without attempting a network fallback.
- The UI clears `submissionInFlight` in `finally`, so every return/failure path restores the action state.
- HTTP rejection messages retain the bounded Worker error while also exposing the HTTP status. Redirects remain disabled and the 2 MiB full-report limit remains fail-closed with no truncation.

## Compatibility verification

- VulkanScope Database 0.39.9 Worker contract tests pass unchanged.
- A synthetic schema-2 / technicalReport-3 VulkanScope 0.41.12 producer fixture using versionCode 422 is accepted by the 0.39.9 future-compatible producer contract with HTTP 201.
- No Database schema, normalizer, D1 migration, endpoint or transport-limit change is required.
- Vulkan 1.4.360 query baseline and 0.41.11 reporting-state semantics are unchanged.
