# VulkanScope 0.41.7 Image Format Properties2 audit

## Trigger

A Database comparison between a VulkanScope 0.41.3 Turnip report and a VulkanScope 0.41.6 report showed successful `VK_FORMAT_S8_UINT` Android Hardware Buffer Image Format Properties2 rows on the older report but `Not reported` on the newer report.

## Root cause

The native `imageFormat2` group queried the handle-less tuple first and executed all `VkPhysicalDeviceExternalImageFormatInfo` variants only inside `if (baseResult == VK_SUCCESS)`. The Vulkan specification defines the external-handle variant as a separate `vkGetPhysicalDeviceImageFormatProperties2` query. A failure of the handle-less tuple therefore cannot be used as a reason to skip OPAQUE_FD or Android Hardware Buffer queries.

The same gating existed in 0.41.3, so this was not introduced by 0.41.6. A newer Turnip build can expose it by returning a different result for the handle-less tuple while still having independently queryable external-handle capabilities.

## Correction

0.41.7 executes each enabled external-handle query independently after the handle-less attempt, regardless of the handle-less result. Successful rows retain the existing detailed-property representation. To make query coverage inspectable without materially inflating schema-2 submissions, the collector also emits compact aggregate query diagnostics for base, OPAQUE_FD and Android Hardware Buffer variants.

The diagnostics distinguish successful queries, `VK_ERROR_FORMAT_NOT_SUPPORTED`, and other VkResult failures without inferring unsupported capability from an omitted row.

## Specification basis

Current Vulkan 1.4 documentation states that external image capabilities are queried by chaining `VkPhysicalDeviceExternalImageFormatInfo` into `VkPhysicalDeviceImageFormatInfo2` and `VkExternalImageFormatProperties` into `VkImageFormatProperties2`. Each external handle type is queried through its own `vkGetPhysicalDeviceImageFormatProperties2` call. The current project Vulkan baseline remains 1.4.360.

## Release gates

- external-handle loop must not be nested under a `baseResult == VK_SUCCESS` gate;
- OPAQUE_FD and Android Hardware Buffer aggregate diagnostics must be present;
- existing Kotlin primitive-state import compile gate remains active;
- report schema and Database endpoint remain unchanged;
- release verifier, XML/JSON/Python checks and source-package hygiene must pass.

## Build environment limit

The release verifier, XML/JSON parsing, Python syntax and package hygiene were run locally. A full `assembleRelease` attempt could not start because Gradle 9.7.0 was not cached and the isolated environment had no DNS access to the Gradle distribution service. No APK compile success is claimed from this environment.
