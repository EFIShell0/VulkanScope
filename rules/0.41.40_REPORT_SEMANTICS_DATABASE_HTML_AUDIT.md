# VulkanScope 0.41.40 report semantics / HTML / Database compatibility audit

## Scope
This release audits the accepted VulkanScope 0.41.39 producer against the supplied complete 0.41.39 HTML report, canonical Vulkan 1.4.361 registry typing, the VulkanScope Database 0.39.14 report-text contract and `PROJECT_RULES.md`.

## Immutable baseline
- Predecessor: VulkanScope 0.41.39 / versionCode 449.
- Predecessor ZIP SHA-256: `11e94bad2605e87c1e3a484a2905843ac6a1495180d2855c6a0a7e62b8ff26d6`.
- Successor: VulkanScope 0.41.40 / versionCode 450.
- Vulkan baseline remains 1.4.361; header version remains 361.
- Database submission schema remains 2; technicalReport schema remains 3.

## Demonstrated BUG — physical-device Properties emitted as Features
The supplied 0.41.39 HTML report contains `VkPhysicalDevice*Properties*` members in the Features table with `SUPPORTED`/`NOT SUPPORTED` presentation. Numeric properties such as descriptor limits therefore lost their numeric meaning. The root cause is semantic type inference from C++ typedef identity: Vulkan defines `VkBool32` with an integer underlying type, so generic C++ type traits cannot distinguish every plain `uint32_t` property from a boolean Vulkan member.

0.41.40 resolves member types from the locked registry for generated/parity routing. Canonical `VkBool32` members are emitted explicitly. The boolean emitter then uses the struct semantic role: Features structs become feature evidence, while Properties structs remain detailed properties with literal true/false values. Generic auto emission is property-only and retains numeric values, arrays and extents.

## Demonstrated MISSING DETAIL — structured property formatting
The supplied report contains several `VkExtent2D` properties as opaque raw bytes and `VkConformanceVersion` as four raw bytes. 0.41.40 formats extents structurally and serializes conformance version as `major.minor.subminor.patch`. UUID/raw byte evidence is retained where no stronger formatter is introduced.

## Demonstrated USABILITY / WRONG PRESENTATION — HTML status colors
0.41.39 styles `AVAILABLE` with a red badge and styles profile `FAIL` using the unknown/gray fallback. 0.41.40 gives each evidence state an explicit semantic class. Available/Supported/Pass are positive; Fail/Unsupported/Not exposed are negative; Unavailable is a distinct amber query-failure state; Not applicable is a separate neutral state; Incomplete is separate partial evidence; Unknown remains gray. Explicit status text remains present for accessibility and auditability.

## Evidence-count semantics
The supplied 0.41.39 report contains 1482 detailed evidence rows: 1478 property/query rows plus four `Vulkan Query Safety` diagnostics. Those four diagnostics are intentionally separate and are not new Vulkan properties. The release does not freeze a historical 1477/1478 number. Correcting property/feature classification can legitimately move rows between Features and Detailed query results without changing the queried device capability.

## Unavailable / unsupported audit of supplied report
The supplied complete report does not show a detailed-property query falsely converted to Unavailable. Vulkan Video is explicitly Not applicable because complete device-extension enumeration did not report `VK_KHR_video_queue`. Image Format Properties2 retains exact tuple states and separates Unsupported (`VK_ERROR_FORMAT_NOT_SUPPORTED`) from query failure. Profile UNKNOWN and FAIL are separate evaluator outcomes. The demonstrated defect is presentation/classification, not a reason to reinterpret missing evidence as unsupported.

## Database HTTP 400 compatibility finding
Database 0.39.14 still validates the historical TXT identity line `Loader / instance API: ...`. VulkanScope 0.41.39 correctly emits separate `Loader API: ...` and `Base probe instance API: ...` lines. The valid current producer can therefore receive HTTP 400 `[report_text]` despite a complete schema-2/schema-3 payload. This is a companion Database contract drift, not a reason to revert the producer to the ambiguous legacy line. Database 0.39.15 is the coordinated fix; historical producer compatibility remains required.

## Regression evidence
The mandatory failing-before-fix evidence is executable rather than prose-only.
`tools/verify_report_semantics_04140.py --root <immutable 0.41.39>` is required to fail. The successor must pass the same semantic verifier plus `tools/test_report_semantics_state_machine.py`. Negative mutations cover field-role routing, HTML status mapping and golden-contract production drift.

## Evidence classes
Static/spec/report-semantic and package evidence are reported independently from Android build/lint/unit and real-device execution. A build or device class that cannot run is recorded as NOT EXECUTED rather than inferred from source gates.
