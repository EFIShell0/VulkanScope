# VulkanScope 0.33.7 Full Application Audit

## Scope

This audit covers VulkanScope 0.33.6 as producer and VulkanScope Database 0.35.6 as consumer, with VulkanScope 0.33.7 containing the safe corrective changes.

Reviewed areas:

- Vulkan loader, instance and physical-device collection
- Core Vulkan 1.0-1.4 feature/property paths
- Runtime instance/device extension enumeration
- Validated extension pNext query dispatch
- Vulkan 1.4.359 published-registry delta versus the pinned 1.4.360 staging baseline
- Limits, formats, memory, queues, Vulkan Video and Surface/WSI evidence
- Vulkan Profile evaluation and registry-coverage metadata
- Android Display/HDR/wide-gamut evidence
- In-app UI completeness and searchability
- TXT, HTML and structured Database report parity
- Update discovery/download/install validation
- Native isolation, size/time bounds and lifecycle safety
- Turnip/private-storage handling and ZIP validation
- Android TV browse usability
- Release verifier/tooling consistency

## Findings corrected

1. Update ordering compared only numeric cores and could not correctly order rc.2 over rc.1 or a stable release over the same-core pre-release. 0.33.7 uses pre-release-aware ordering and ignores build metadata for precedence.
2. Android display state was refreshed only on resume and read DEFAULT_DISPLAY. 0.33.7 listens for display changes while started and prefers the Activity-associated display so foldable/external-display changes refresh report state.
3. Android HDR_TYPE_INVALID could be surfaced as an unknown HDR capability. It is now filtered before UI/export/submission while unknown future non-invalid values retain their raw numeric identity.
4. The self-contained HTML report had no CSP/referrer policy and duplicated the GPU hero metric. 0.33.7 adds restrictive local-only metadata and renders the GPU metric once.
5. Properties & Limits used an All filter that displayed detailed properties but omitted available limits. All now exposes both datasets.
6. Database endpoint validation trusted the build-time constant host after only checking HTTPS/non-empty host. The exact official Worker host is now checked at runtime as defense in depth.
7. tools/verify_release.py still expected VulkanScope 0.33.3/versionCode 333 and tools/verify_canonical_vulkan_headers.py still expected VK_HEADER_VERSION 357. Both release gates now target the actual 0.33.7 / 337 / header 360 baseline.
8. Current-source documentation still described Vulkan 1.4.358 as the current published Khronos specification. The current-source record is updated to Vulkan 1.4.359 (2026-08-07) while retaining the distinct project staging/query baseline 1.4.360.

## Vulkan query coverage result

The current public Vulkan 1.4.359 delta is already represented by VulkanScope's validated staging catalog: VK_EXT_cooperative_matrix_maintenance1, VkPhysicalDeviceCooperativeMatrixMaintenance1FeaturesEXT and vkGetPhysicalDeviceCooperativeMatrixProperties2EXT are present. VK_EXT_image_tiling_control and VkPhysicalDeviceImageTilingControlFeaturesEXT are also present. Vulkan 1.4 core feature/property structures, exact extension tokens, generated detailed properties, memory, queues, formats, Surface diagnostics and registry-coverage data remain unchanged by this release.

No new Vulkan capability is inferred from GPU identity, Android version, extension naming, HDR branding, or registry presence alone. Runtime evidence and query diagnostics remain authoritative.

## Report/database result

TXT, HTML and technicalReport use the same completed VulkanReport/DisplayReport snapshot passed to the export/submission action. Structured schema remains technicalReport schemaVersion 3 inside submission schemaVersion 2. VulkanScope Database 0.35.6 remains compatible. No D1/schema migration is required.

## Build statement

Static/source validation is performed in the assistant environment. A successful APK compilation must not be claimed unless Gradle and all build dependencies complete in that environment.
