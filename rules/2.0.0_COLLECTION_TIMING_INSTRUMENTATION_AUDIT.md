# VulkanScope 2.0.0 collection timing instrumentation audit

## Release scope
- Version: 2.0.0.
- versionCode: 2000.
- Functional predecessor: VulkanScope 1.5.5.
- Purpose: measure where VulkanScope collection time is spent before making collector-architecture performance changes.

## Instrumented phases
- Cold-start startup gate delay.
- Complete collection orchestration.
- Base collection total.
- Each bounded base probe attempt.
- Base JSON/report decode.
- Metadata enrichment.
- Surface enrichment.
- Background-detail collection total.
- Every dedicated advanced/extension probe round trip already scheduled by the existing collector.
- Isolated service dispatch-to-worker, native library load, JNI collector wall-clock duration, terminal validation and pre-terminal service duration.

## Security and privacy
- Timing telemetry is not part of the Vulkan capability report and is not sent to VulkanScope Database.
- Probe telemetry uses a dedicated sidecar whose canonical path must remain under `cacheDir` and exactly equal the result path plus `.timing`.
- The telemetry payload is capped at 16 KiB.
- The service writes the sidecar atomically without replacing result/terminal ownership rules.
- The Activity treats the sidecar as optional evidence, reads only bounded JSON fields, and deletes it with the result/crash/terminal files.
- A missing timing sidecar cannot upgrade or downgrade capability status and does not affect crash/timeout/cancellation handling.

## Correctness boundaries
- No Vulkan registry, generated query catalog, native C++ collector, report/Database schema, ABI, permission, dependency, AGP, Gradle or updater-security change is made for 2.0.0.
- JNI collector timing is explicitly wall-clock timing around one collector entry point. It is not equivalent to timing each Vulkan command.
- Timing is measured with `System.nanoTime()` and converted to non-negative milliseconds.
- Existing one-shot process isolation remains unchanged. This release gathers evidence before deciding whether session-level isolation or batched pNext collection should replace the current process-per-group design.

## UI evidence
- Analysis → Collection diagnostics shows complete/base/enrichment/background phase timings when measured.
- Dedicated probe count and slowest dedicated probe are shown from measured round trips.
- Detailed timing rows remain in the existing lazy diagnostics list.
- Missing timing rows remain absent/unknown; no synthetic zero is used except the explicit no-live-Surface enrichment phase where no Surface probe was executed.

## Release acceptance
- `tools/verify_release_2000.py` must PASS.
- `tools/test_release_2000_state_machine.py` must PASS.
- `tools/test_release_2000_negative_mutations.py` must PASS.
- Registry/spec/report/Profile/Surface/Video, probe lifecycle/timeout/cancellation, hardening and concurrency/resource gates remain mandatory.
- Android build/runtime timing is recorded only if actually executed.
