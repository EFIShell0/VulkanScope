# VulkanScope 0.41.21 Surface, external-capability and evidence-state audit

## Scope
0.41.20 was re-audited against `PROJECT_RULES.md` for report correctness/completeness, stale-report loss, Vulkan/Android provenance, canonical naming, native ownership, bounds, security, performance and usability.

## Corrections
- Removed the unreachable duplicate Surface/WSI branch from the base collector. Real `ANativeWindow`/`VkSurfaceKHR` ownership now exists only in the isolated Surface probe.
- Added explicit `VK_EXT_swapchain_colorspace` evidence state so an absent entry in incomplete instance-extension enumeration remains Unknown rather than becoming Not exposed.
- Preserved the exact `VkResult` for every queue-family presentation-support query and prevented query failure from being displayed as negative support evidence.
- Made the per-device Surface query state Incomplete when queue support, applicable capabilities, format enumeration or present-mode enumeration fails or hits a safety bound while retaining bounded partial positive evidence.
- Enforced the Vulkan non-null-Surface valid-usage prerequisite for capabilities, format and present-mode commands: dependent WSI queries now run only after successful positive `vkGetPhysicalDeviceSurfaceSupportKHR` evidence. Complete negative presentation evidence becomes Not applicable; incomplete support evidence remains Unknown without issuing invalid dependent commands.
- Included instance-extension enumeration completeness in the final Surface completeness state so missing optional WSI-extension evidence cannot be hidden behind otherwise successful queries.
- Added explicit first-format-query attempted state and stopped serializing the internal `-1` compatibility sentinel as a canonical `VkResult`; unattempted structured results are null/Not attempted.
- Split external memory/fence/semaphore capability collection so one unavailable entry point cannot erase independent valid evidence.
- Replaced the incorrect Opaque-FD labels on SYNC_FD fence/semaphore queries with exact Vulkan handle-type tokens and expanded the FD paths to query both `VK_EXTERNAL_*_HANDLE_TYPE_OPAQUE_FD_BIT` and `VK_EXTERNAL_*_HANDLE_TYPE_SYNC_FD_BIT` where the corresponding KHR FD extension is exposed.
- Expanded external-memory evidence to query `VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_FD_BIT`, `VK_EXTERNAL_MEMORY_HANDLE_TYPE_DMA_BUF_BIT_EXT` and `VK_EXTERNAL_MEMORY_HANDLE_TYPE_ANDROID_HARDWARE_BUFFER_BIT_ANDROID` independently behind their exact extension prerequisites.
- Corrected Vulkan 1.0 query-instance compatibility by enabling advertised `VK_KHR_device_group_creation` and external memory/fence/semaphore capability instance extensions, and by loading `vkEnumeratePhysicalDeviceGroupsKHR` when the core 1.1 command name is unavailable. This prevents promoted-to-core commands from being treated as implicitly usable on a 1.0 instance.
- Replaced the `vkGetPhysicalDeviceFormatProperties2` comma-operator pseudo-condition with a direct void query following the existing entry-point gate.
- Distinguished old-Android API unavailability and unavailable HDR metadata from proven display-capability absence.
- Propagated Surface color-space-extension state and queue-family `VkResult` evidence through UI, Analysis, TXT, HTML and schema-3 technicalReport.

## Static security and ownership review
The fixed HTTPS Database endpoint/no-redirect client, complete-report opt-in submission gate, 2 MiB all-or-nothing request bound, cleartext prohibition, APK/update validation, Turnip private-path confinement, isolated probe service, JNI string release pairs, `ANativeWindow_release`, Vulkan instance/Surface/device/self-test cleanup and bounded driver-provided counts were rechecked. No new concrete static security vulnerability or ownership leak was found in the reviewed paths. Static review does not replace device/driver sanitizer, profiler or accessibility testing.

## Baseline
Khronos published Vulkan Registry remains 1.4.360 dated 2026-08-14. Android compile/target remains API 37. AGP remains 9.3.2 with Gradle wrapper 9.7.1. Submission schema remains 2 and technicalReport remains schema 3.

## Final integrity corrections
- Hardened robust physical-device enumeration so four bounded `VK_INCOMPLETE` attempts retain the last bounded positive device-handle set instead of collapsing it to an empty result. The base report now carries exact `physicalDeviceEnumerationResult` and `physicalDeviceEnumerationComplete` provenance, remains `baseReportComplete=false` while incomplete, and exposes the provenance in Vulkan UI, Analysis, TXT, HTML and technicalReport.
- Extended the same partial-positive-evidence rule to isolated core, extension, Vulkan 1.4, advanced and simple-feature query groups. Incomplete physical-device enumeration cannot prove device/API/extension absence and therefore cannot be converted into Not applicable.
- Prevented cross-process misattribution on systems exposing multiple physical devices with the same vendor/device IDs. Surface, advanced and extension merges require a unique identity on both sides; self-test rejects ambiguous matches instead of silently selecting the first device.
- Added safe fallback from advertised-but-unusable `VK_KHR_get_surface_capabilities2` entry points to classic `VK_KHR_surface` queries while retaining explicit provenance for the unavailable optional path.
- Corrected a duplicate Kotlin `status` local declaration in the extension-group merge path that could block release compilation even though text-based semantic checks passed.
