# VulkanScope 3.0.11 Turnip Validated Folder Count Audit

## Scope and immutable predecessor

VulkanScope 3.0.11 starts from immutable VulkanScope 3.0.10 (`e10372fa362816ac5c718aafe8e5b9d04e1cda404d94b8ccfc9cc0065ff02ba2`, 846 files). The production runtime change is restricted to `MainActivity.kt`; `app/build.gradle.kts` changes release identity only. Native/JNI Vulkan collection, registry/generated data, report/export schemas, Database transport, manifest, permissions, ABI targets, packaged assets and dependency versions remain predecessor-equivalent.

## Failing-before-fix evidence

The user-provided File Manager screenshots show the `Download` folder labeled `63 files`, while opening that same folder shows three Turnip package rows accepted by the manager's archive inspection. The predecessor folder summary increments its counter for every readable direct child whose filename ends in `.zip`; it does not call the Turnip archive inspector before incrementing. Unrelated ZIP archives therefore inflate the folder subtitle even though they are hidden from the Turnip package list after validation.

## Repair boundary

Folder summaries now keep separate bounded counters for ZIP candidates inspected and Turnip packages validated. At most 256 direct child ZIP candidates are inspected, preserving the existing bound. Each candidate contributes to the visible folder count only when `inspectTurnipArchive` accepts it. That inspector preserves the existing canonical-file/symlink checks, compressed-size bound, ZIP path validation, entry/decompressed-size limits, exactly-one-`meta.json` requirement, schema validation and metadata-declared non-empty Vulkan `.so` validation.

Already-imported packages remain counted when they are otherwise valid because the File Manager continues to display those rows as disabled/imported evidence inside the folder. The count remains informational only; installation still revalidates the selected package before committing it.

The scan remains on the established `Dispatchers.IO` path and propagates coroutine cancellation. No recursive folder traversal is introduced.

## Evidence boundary

`tools/verify_release_3011.py` locks release identity, validated-count source semantics, the 256-candidate bound, authoritative import validation and protected predecessor-equivalent files. `tools/test_release_3011_state_machine.py` models the reported 63-ZIP/3-valid case, imported-package inclusion and bounded overflow behavior. `tools/test_release_3011_negative_mutations.py` proves that reverting to extension-only counting, displaying the inspected count or removing the bound fails while documentation-only drift remains accepted. `tools/verify_release_3011_regression.py` restricts production drift to `MainActivity.kt` and release identity.

Android Gradle compilation and replay against the user's real shared-storage tree remain separate evidence classes and may be called PASS only when actually executed successfully.
