## Runtime regression oracle
The supplied 390×848, approximately 8.08-second device recording shows the collection pager in its normal list position at the beginning. During downward scrolling the pager moves toward the top region and then disappears while collection result cards continue moving behind the translucent application header. The failure reproduces the user's reported sticky-follow behavior rather than a page-count or data-loss problem.

The predecessor attempted to keep the sticky header below the application header by applying a positive `Modifier.offset(y = headerContentInset)` to content inside the lazy sticky item. Android's current Compose modifier documentation states that `offset` changes placement without changing the composable's measurements. The sticky item therefore remained owned by the lazy layout at its original measured position while its visual child was translated. This is not a reliable way to create a persistent visual lane outside the lazy viewport/clipping boundary.

Official references rechecked 2026-09-27:
- Android Developers, Compose modifiers: `Modifier.offset` changes position without changing measurements.
- Android Developers, Lazy lists and lazy grids: `stickyHeader` is the LazyColumn sticky-header mechanism.
- Android Developers, modifier phases/animation guidance: offset is a placement operation and does not propagate a new measured position to the parent.

## Repair classification
- `REGRESSION/USABILITY`: move the pinned visual representation out of the LazyColumn clipping boundary while retaining the lazy sticky item as the normal-flow anchor.
- `REGRESSION/STATE`: remember each observed pager's item index and layout generation so loss of ordinary visibility does not erase pin state.
- `USABILITY/RESPONSIVE`: derive the pin threshold from the live application-header inset and horizontal system-navigation insets rather than portrait-only constants.

## Implementation boundary
`VulkanLazyPage` now owns a bounded keyed registration map for pagers rendered by that page. A pager registers its lazy item index, measured height, current lazy-layout item count, total item count, current page, page size and current page-change callback. The page host selects the latest eligible pager whose anchor has crossed the live header boundary. While the anchor remains visible its real lazy offset is authoritative; after it leaves ordinary visibility, the remembered index plus the current first-visible item/offset keeps the pin state alive.

The pinned copy is rendered as a sibling overlay of the LazyColumn, directly below the live header and inside current left/right navigation-bar insets. The normal-flow sticky item is made transparent only while the overlay is active, preventing duplicate visuals. The overlay reports its measured pager height through the existing coordinated-lane reporter, preserving app header → pager → transient status → top-scroll-indicator ordering. Page-number changes keep the existing number-only transition and do not retrigger the pin/unpin animation.

A registration whose recorded `layoutInfo.totalItemsCount` differs from the current lazy layout is ignored. This bounds stale state after list-structure changes while still allowing an observed pager to remain pinned when Compose temporarily omits it from `visibleItemsInfo`.

## Responsive model evidence
The state-machine model covers both compact portrait and landscape-style header boundaries. In both cases:
1. pager below the header boundary → normal flow;
2. pager reaches/crosses the live header boundary → overlay pinned;
3. pager key disappears from ordinary visible-item metadata while the first visible index has passed the remembered pager index → overlay remains pinned;
4. scrolling back until the pager is again below the live header boundary → overlay unpins;
5. a lazy-layout item-count generation change invalidates a retained registration until the live pager re-registers.
