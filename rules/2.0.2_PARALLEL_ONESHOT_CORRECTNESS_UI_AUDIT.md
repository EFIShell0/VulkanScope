# VulkanScope 2.0.2 parallel one-shot correctness and UI audit

## Release scope
- 2.0.1 is superseded because reusing one dedicated process for multiple query groups violated the established process-teardown ownership assumption and produced both worse latency and lost capability evidence on target hardware.
- 2.0.2 restores the 2.0.0 one-query-per-process collector contract and optimizes only orchestration concurrency.
- The release also fixes transient-overlay obstruction on the Surface landing destination and suppresses the application-owned evidence right-click quick menu on desktop/PC/ARC-style Android environments.

## Collector correctness requirements
- Every automatic background query group must run in its own dedicated process lifetime. A process must terminate after its single query publication just as in 2.0.0.
- Native C++ collector bytes, Vulkan registry/generated query data and validated extension census remain identical to 2.0.0. No query group, validated physical-device extension provider, core version, advanced group or report field may be removed to improve speed.
- Background performance optimization may use at most four independent Android service/process lanes. Each lane keeps its own mutex, process name, timeout, result/terminal/timing sidecars and one-shot process teardown.
- Active background lane count is resource-adaptive: at most two lanes for Android memoryClass up to 256 MiB, three lanes up to 384 MiB, otherwise four lanes. This is an orchestration resource limit only and must not change query coverage or support semantics.
- Base, metadata, Surface, self-test and explicit ad-hoc queries remain on the primary one-shot service path.
- Background query results may finish out of order, but merge order must remain the deterministic original query-list order after all bounded one-shot results are available. This prevents concurrency from changing overlapping report-field precedence.
- Each automatic group retains its original 12-second or advanced 30-second per-query limit and remains subject to the existing 60-second total background budget.
- Crash, timeout, cancellation, terminal validation, 64 MiB result bound, 16 KiB timing bound and private-cache canonical-path confinement remain mandatory for every lane.

## Capability parity requirements
- `VALIDATED_PHYSICAL_DEVICE_QUERY_EXTENSIONS` scheduling remains filtered only by extensions enumerated in the complete base report, exactly as in 2.0.0.
- Extension query groups retain the `ext::<canonical extension name>` form and are never coalesced into a result that can lose provider-specific evidence.
- 2.0.2 must retain the locked Vulkan 1.4.364 registry state: 477 registered extensions and 305 validated Android-queryable physical-device providers.
- Missing or failed parallel query evidence remains Unavailable/Unknown according to existing semantics and must never become Unsupported merely because a lane fails.

## Surface overlay requirements
- The Surface root chooser is not a `VulkanLazyPage`; it must explicitly consume the shared transient-overlay top inset, floating-navigation bottom inset and Android navigation-bar side insets.
- Collection/network/update overlays must not cover the first Surface chooser row, and the floating bottom navigation must not cover the final chooser row.
- Surface subsection pages continue to use the established `VulkanLazyPage` inset behavior.

## Desktop secondary-click requirements
- On ChromeOS ARC, Android PC form factor or freeform-window-management environments, secondary mouse clicks on `CapabilityKeyValue` evidence rows are consumed without opening the application-owned Copy/Share/Watch/Encyclopedia quick menu.
- Touch long-press evidence inspection remains available. Accessibility `CustomAccessibilityAction("Evidence actions")` remains available.
- Ordinary Android environments may retain the existing application quick menu for a secondary pointer if one is present.

## Security, privacy and build boundaries
- No permission, endpoint, upload path, identifier collection, file authority, ABI, dependency, AGP/Gradle, updater trust rule or Database schema is changed.
- No new persistent executor, global coroutine scope, unbounded queue or unbounded file is introduced.
- Four service components are non-exported and use private app processes only.

## Evidence
- Targeted 2.0.2 verifier, state-machine test and negative-mutation test are mandatory.

- Android compile/assemble, real-device timing, real-device capability parity and desktop pointer runtime remain separate evidence classes and must be reported NOT EXECUTED when unavailable.
