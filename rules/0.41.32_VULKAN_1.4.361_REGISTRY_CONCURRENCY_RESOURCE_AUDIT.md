## SPEC-MISSING — Vulkan 1.4.361 delta
The locked registry contains `VK_NV_private_data_base_handle`, a device extension providing `VkPhysicalDevicePrivateDataBaseHandleFeaturesNV`. Its Boolean member `privateDataBaseHandle` is capability evidence and was absent from the 0.41.31 runtime coverage. 0.41.32 adds the extension to validated coverage, schedules its feature structure through the physical-device pNext chain when enumerated, and serializes the member into the same report path as other extension feature structures.

Regression evidence: `verify_1_4_361_regressions.py` fails against the 0.41.31 predecessor and passes against 0.41.32.

## TEST-GAP — stable/provisional registry classification
Deriving Features2/Properties2 providers from the complete 1.4.361 registry yields 302 queryable physical-device provider extensions on the Android build target. They divide into 297 stable and 5 provisional providers. The complete provisional set is:
- `VK_AMDX_dense_geometry_format`
- `VK_AMDX_shader_enqueue`
- `VK_KHR_portability_subset`
- `VK_NV_cuda_kernel_launch`
- `VK_NV_displacement_micromap`

The generated manifest, coverage snapshot and strict verifier now preserve that distinction. Provisional runtime structures remain dependent on explicit `VK_ENABLE_BETA_EXTENSIONS`; stable and provisional status are not conflated.

## TEST-GAP / MISSING DETAIL — complete extension reference
The predecessor reference asset was only a subset and the generator contained the invalid Python method name `removePrefix`. 0.41.32 fixes the generator and produces all 474 registered Vulkan/vulkanbase extension records from the locked registry. Kotlin output is chunked to bound generated method size. Registry metadata is not guessed: revision, type, platform, promotion, dependency, obsoletion/deprecation, provisional state, related commands and tokens originate from `vk.xml`.

Runtime enumeration remains a separate evidence class. A registered extension that is not enumerated by the current device is not described as globally Unsupported.

## MEMORY / PERFORMANCE — full-report publication copies
The predecessor returned a complete successful native JSON result through `NewStringUTF`, after already building it as a C++ `std::string`, and the service then persisted the returned Kotlin string. Near the publication ceiling this adds avoidable large-copy pressure in the probe process.

0.41.32 changes successful probe publication to:
1. construct the bounded native result;
2. write it directly to the cache-confined temporary checkpoint;
3. atomically rename the checkpoint;
4. return only JNI Boolean publication success;
5. open the published file in the main process and read one exact-size bounded byte array before UTF-8 decoding.

The 64 MiB publication bound rejects oversized output without truncation. Failure to publish never turns an incomplete/oversized result into a complete report.

## Resource-limit sufficiency conclusion
`registry/generated/resource_budget.json` records the checked limits and census. Current registered extension census is 474 while native extension enumeration is bounded at 4096 entries, providing substantial current-census headroom.

The audit does **not** claim that 64 MiB is mathematically sufficient for every theoretically possible future or adversarial driver output permitted by every independent enumeration bound. Layer×extension and other bounded cross-products can make such a universal proof materially larger than a normal report. The correct safety behavior is therefore maintained: 64 MiB is a hard memory/publication ceiling, output is never truncated to manufacture completeness, and oversize evidence fails explicitly.

The Database 2 MiB transport limit and Analysis 8 MiB snapshot limit are independent downstream bounds. Neither is reinterpreted as an all-device completeness guarantee. A coordinated Database client/server audit is required before changing the Database transport contract.

## RACE / TIMEOUT / REPORT-LIFECYCLE audit
Verified static contracts:
- `probeMutex` serializes application service probes.
- `VulkanProbeService` uses one worker executor.
- Native probing uses a fair `ReentrantLock(true)`.
- Per-probe timeout begins after the serialized caller owns the probe slot and launches the service, so mutex queueing does not consume another probe's timeout allowance.
- Result files are unique per request and successful native publication uses temporary-file + atomic rename.
- Polling/result handling does not accept a partially written successful file.
- Timeout/crash cleanup stops the service and process termination is constrained to the app UID plus exact `:vulkan_probe` process name.
- Base-report recovery still requires authoritative `baseReportComplete`; partial/incomplete extension/device enumeration cannot be promoted into complete export/Database eligibility.
- Existing stale-generation/report-change gating remains in place.

No additional concrete race, timeout leak, stale-result promotion or report-loss defect was proven after these checks, so no speculative concurrency refactor was introduced.

## CORRECTNESS / TERMINOLOGY
The service is hosted in a dedicated `:vulkan_probe` Android application process but the manifest does not request Android `isolatedProcess=true`. 0.41.32 removes user/report wording that called it an isolated process. This prevents an unsupported security-property claim while retaining the actual crash/lifetime separation of the dedicated process.

## SECURITY audit
Static/release gates retain:
- cleartext traffic disabled;
- one approved INTERNET permission;
- fixed official HTTPS Database API root with no user-editable endpoint;
- no-redirect Database submission and complete-report gate;
- bounded all-or-nothing payload behavior;
- updater package/signing/version validation and private-cache handling;
- Turnip/custom-driver canonical-path confinement, duplicate-path rejection and file-count/per-file/aggregate-size bounds;
- bounded native Vulkan enumerations and deterministic JNI/native ownership paths;
- three release ABIs only: arm64-v8a, armeabi-v7a and x86_64.

No new concrete security vulnerability was proven by the static audit. This does not substitute for dynamic Android/runtime security testing.
