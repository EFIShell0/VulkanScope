# VulkanScope 0.41.31 full spec/report/security/memory audit

## Scope and baseline
- Predecessor: VulkanScope 0.41.30, SHA-256 `33ee782877109d5a833e29c180af733598eaeb0aa0e27fa1ca9b2286587bbab5`.
- Published Vulkan baseline: Vulkan 1.4.360, 2026-08-14, Vulkan-Docs commit `090f1b190d60ced4a1d198fd3747d071cc271b1c`.
- Pinned canonical header: Vulkan-Headers commit `0b7f383797fa7be53ae28213e001ae60668ee511`, `VK_HEADER_VERSION` 360.
- Android compile/target API 37, submission schema 2, technicalReport schema 3 and the arm64-v8a / armeabi-v7a / x86_64 ABI policy are unchanged.
- Production changes are evidence-gated. `tests/golden/0.41.30_regression_contract.json` locks 81 predecessor runtime files and permits only `app/src/main/cpp/vulkanscope.cpp` to change in this release.

## Proven defects fixed
### SPEC-MISSING: maintenance5 format eligibility
0.41.30 gated numeric Vulkan formats 1000470000 and 1000470001 exclusively on core Vulkan 1.4. Those values are `VK_FORMAT_A1B5G5R5_UNORM_PACK16` and `VK_FORMAT_A8_UNORM`, which are also provided by `VK_KHR_maintenance5`. A Vulkan 1.3 implementation exposing that extension could therefore have valid format-property queries silently skipped. 0.41.31 accepts core 1.4 or `VK_KHR_maintenance5`.

### INCORRECT-REPORTING: canonical image-layout name
0.41.30 omitted the registered `VK_IMAGE_LAYOUT_TENSOR_ALIASING_ARM` name from the canonical image-layout mapper. 0.41.31 reports that exact identifier. Unknown future numeric layouts still remain raw evidence rather than receiving fabricated Vulkan names.

### INCORRECT-DETAIL: WSI color-space semantics
0.41.30 described `VK_COLOR_SPACE_DCI_P3_NONLINEAR_EXT` without the Vulkan presentation-engine XYZ component interpretation and presented `VK_COLOR_SPACE_DOLBYVISION_EXT` too directly as a Dolby Vision presentation class. 0.41.31 records the XYZ presentation interpretation and identifies the Dolby Vision color-space token as the legacy Vulkan enum without treating the enum alone as proof of Dolby Vision metadata signaling.

### TEST-GAP: provisional registry coverage
0.41.30 carried 301 validated physical-device extension providers, including `VK_AMDX_dense_geometry_format` and `VK_AMDX_shader_enqueue`, while its strict upstream generator/verifier excluded every `provisional="true"` registry extension. That made the checked-in 301-extension contract incompatible with a real strict locked-upstream regeneration. 0.41.31 includes registered physical-device provider extensions represented by the pinned header, records 299 stable plus 2 provisional providers separately, and requires explicit `VK_ENABLE_BETA_EXTENSIONS` mode whenever provisional providers are queried.

## Regression evidence
`tools/verify_spec_regressions.py` was executed against both trees. The 0.41.30 predecessor fails all four targeted contracts: maintenance5 format eligibility, tensor-aliasing canonical name, DCI-P3 XYZ semantics and legacy Dolby Vision semantics. The 0.41.31 successor passes all four. `tools/verify_regression_contracts.py` independently verifies the 0.41.30 predecessor SHA, current version metadata, normalized build configuration, all 81 runtime hashes, the single allowlisted runtime change, 104 query groups, 301 validated extension providers, 109 implemented physical-device structs and 10 instance dependency candidates. Negative gate tests also deliberately changed one non-allowlisted runtime file, changed the allowlisted runtime file to a non-contract hash and corrupted the provisional-extension count; all three mutations were rejected, then the untouched successor passed again.

## Canonical names and unsupported/unknown evidence
- Runtime extension enumeration remains authoritative and exact runtime `VK_*` names are retained.
- Known image-layout and color-space values use registered identifiers; genuinely unknown values keep raw numeric evidence.
- `VK_INCOMPLETE`, unavailable, not-applicable and unsupported states remain separate and no failed/incomplete enumeration is converted into proof of global absence.
- Current VkResult mapping and existing format/present-mode/color-space raw fallback paths were rechecked; no additional proven fabricated identifier was found in the reviewed paths.

## Query, report and report-loss audit
- Base completeness remains authoritative and requires complete physical-device/device-extension evidence before complete export or Database submission.
- Partial positive evidence from bounded `VK_INCOMPLETE` enumerations remains visible while absence is not inferred.
- Stale collection generations and delayed driver/picker callbacks retain the existing mutation/generation gates.
- TXT, HTML, Analysis and Database paths continue to derive from the same complete report state; pending exports retain private snapshots and destination writes occur on IO dispatchers.
- No additional concrete report-loss or stale-report promotion defect was found in the reviewed lifecycle paths.

## Security audit
- Android cleartext traffic remains disabled; backups remain disabled. FileProvider and isolated Vulkan probe service remain non-exported.
- Database submission remains fixed to `https://vulkanscope-database-api.vulkanscope.workers.dev`, HTTPS-only, root-constrained, no redirects, explicit/user-initiated, complete-report-gated and bounded to a non-truncating 2 MiB payload.
- Update discovery remains limited to the official EFIShell0/VulkanScope GitHub release API. APK asset URLs are constrained to official HTTPS release paths; downloads are bounded to 256 MiB; package name, signing certificate, versionCode and exact selected versionName are checked before installation.
- Turnip/AdrenoTools import retains canonical-path confinement, duplicate-path rejection, 2048-entry / 64 MiB aggregate / 32 MiB per-file bounds, exact metadata/library validation, read-only native-library hardening, private temporary directories and atomic replacement behavior.
- No new concrete path traversal, arbitrary endpoint, cleartext transport, silent upload or package-identity bypass was found in the statically reviewed paths.

## Native memory and ownership audit
- Enumeration allocation counts remain bounded before vector allocation for extensions, layers, physical devices, queues, tools, video formats, sparse formats, Surface formats and present modes.
- Host-image-copy layout arrays retain a 65536-entry local safety bound.
- `VulkanApi` owns the Vulkan loader handle and closes it in its destructor; fallback `dlopen` attempts populate one owned handle. Vulkan instances, devices, surfaces and self-test resources retain explicit destruction paths.
- No concrete native heap leak, unbounded Vulkan enumeration allocation or ownership regression was found by static review.
- Static review is not HWASan/ASan/Perfetto evidence; real sanitizer/profiler execution is recorded separately below.

## Performance and usability audit
- Full/advanced/native collection, update networking, Turnip traversal/import, Database submission and report snapshot I/O remain dispatched off the Compose main thread in the reviewed paths.
- Large report lists continue to use lazy Compose containers. Export serialization uses private snapshots and bounded stream copies rather than forcing destination I/O on the UI thread.
- No new proven recomposition-triggered Vulkan query or unbounded list materialization requiring a runtime patch was found.

## Embedded extension-reference detail limitation
`registry/generated/extension_reference.json` currently contains 199 checked-in reference entries. Only 148 overlap the 301 validated physical-device runtime extension providers, leaving 153 validated runtime extension names without an embedded detail record. The asset itself truthfully labels missing metadata as unavailable; it does not fabricate revision/type/platform/dependency information. All 199 current entries have an empty `specVersion`, `type` and `platform` field, so the embedded reference asset must not be described as complete. The existing locked-`vk.xml` generator remains the authoritative route to fill this data. This audit environment could not fetch the locked raw registry into the build container, so 0.41.31 deliberately preserves explicit unavailable detail rather than inventing metadata.
