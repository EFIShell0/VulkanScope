# VulkanScope 2.0.3 adaptive parallel scheduler audit

## Release scope
- 2.0.3 keeps the 2.0.2 one-query-per-process correctness model and changes only background probe scheduling, stale-process handoff latency and timing attribution.
- No Vulkan query group, validated extension provider, report field, registry/generated byte, native collector byte or probe-service byte is removed or rewritten for speed. The locked census remains 477 registered extensions and 305 validated Android-queryable physical-device providers.

## Adaptive lane requirements
- Maximum background concurrency remains four independent non-exported one-shot probe processes.
- Lane selection must use Android low-RAM classification, current `ActivityManager.MemoryInfo.lowMemory`, physical total memory, currently available memory and processor count. Java `memoryClass` alone is forbidden as the deciding resource signal because it is an app heap-class value rather than physical device memory.
- Low-RAM or active low-memory devices use at most two lanes. Devices below 3 GiB total memory, below 768 MiB available memory or below 12% available-memory ratio also use at most two lanes.
- Devices below 6 GiB total memory, below 1.5 GiB available memory, below 20% available-memory ratio or below six logical processors use at most three lanes. Other devices may use four lanes.
- Lane selection changes concurrency only. Every scheduled core, advanced and validated extension group remains present.

## Scheduler requirements
- Static modulo assignment is superseded. Active workers claim the next not-yet-started query from one bounded atomic index after completing their prior query.
- At most one query may execute on each private lane process at a time. Existing per-lane mutexes remain authoritative as a secondary guard.
- Completion order may differ, but final report merge order remains the original ordered query list.
- The existing 60 second background budget and 12/30 second per-query timeout classes remain unchanged.

## Process handoff requirements
- Before starting a query, VulkanScope must confirm no prior process for that exact lane remains alive.
- When no prior PID exists, quiescence is immediate; an unconditional fixed pre-launch sleep is forbidden.
- If a stale PID exists, the service is stopped, the PID is killed and bounded polling continues until the process is confirmed gone or the existing 1.5 second quiescence deadline fails.
- One-query-per-process teardown remains mandatory. Multi-query process reuse remains forbidden.

## Publication polling requirements
- Host-side file polling may use shorter bounded delays to reduce observation latency, but result-size bounds, timing-size bounds, terminal marker ownership, stable JSON validation, crash markers and timeout recovery remain unchanged.
- No busy-spin loop is permitted. Every polling path retains a positive coroutine delay.

## Timing semantics
- `probe_total/<group>` represents the actual isolated host round-trip from the per-service host timing when available.
- Scheduler/queue overhead is recorded separately as `probe_queue_wait/<group>` and must never be presented as Vulkan native-call time.
- Missing service timing falls back to the bounded scheduled elapsed time rather than inventing a value.

## Correctness and security boundaries
- Native C++, VulkanProbeService, locked Vulkan 1.4.364 registry/generated data, validated extension coverage and AdvancedAnalysis bytes remain 2.0.2-equivalent.
- Four background service declarations stay non-exported/private-process.
- No permission, endpoint, upload path, identifier collection, Database schema, updater trust rule, ABI, dependency, AGP or Gradle version changes are authorized.

## Evidence requirements
- `tools/verify_release_2003.py`, `tools/test_release_2003_state_machine.py` and `tools/test_release_2003_negative_mutations.py` are mandatory.
- Full registry/spec/report/Surface/Profile/Video/probe-lifecycle/timeout/cancellation/hardening/resource/package gates remain mandatory.
- Real-device performance is a separate evidence class and must not be reported PASS from source inspection alone.
