# VulkanScope 0.41.24 Surface enumeration / evidence lifecycle audit

## Scope

This release re-audits live Android Surface/WSI enumeration, physical-device and extension/layer retry semantics, native crash-guard lifetime, multi-device compatibility summaries, report parity, query safety and package security against `PROJECT_RULES.md`. Vulkan/query and pinned header baseline remain 1.4.360; Android compile/target remains API 37; submission schema remains 2 and technicalReport remains 3.

## Corrections

- Surface format and present-mode helpers retain bounded partial positive evidence across later failures and local safety rejection while preserving the last authoritative Vulkan result and explicit incompleteness.
- A successful supported-Surface format query returning zero entries and a successful present-mode query returning zero entries or omitting FIFO are treated as specification anomalies, not completed negative evidence.
- Runtime failure of optional capabilities2/formats2 queries falls back to classic WSI when callable. Earlier bounded formats2 partial evidence is retained if the fallback itself does not produce entries.
- Local physical-device allocation safety rejection is separated from actual driver `VkResult`; no synthetic Vulkan out-of-memory result is emitted for an application-side bound. Safety rejection and reason remain visible even when earlier bounded partial GPU handles are retained.
- Instance extensions/layers, per-layer extensions, device layers and device extensions retain earlier bounded partial rows if a later retry fails or exceeds a local bound.
- DeviceReport carries Surface format/present-mode completeness and specification-anomaly state through UI, Analysis, TXT, HTML and technicalReport. Catalog-wide unsupported inference requires proven complete enumeration.
- Isolated native probe signal handlers are restored after normal completion. JNI string and Android native-window ownership remains paired.
- Legacy schema-2 GPU/driver/device-API summaries receive additive multi-device scope/count provenance; existing keys and schema remain unchanged while schema-3 technicalReport retains every physical device.

## Verification policy

The release verifier gates the new invariants in addition to all previous correctness/security/package rules. A final source ZIP is acceptable only after it is independently re-extracted and the verifier, JSON/XML parsing, Python syntax, `files.txt`, ZIP path/duplicate/symlink and executable-metadata checks pass from the packaged tree. A Gradle build is reported only if Android/Kotlin/CMake tasks actually run successfully; an unavailable Gradle distribution/network is recorded as an environment limitation rather than a successful build.
