# VulkanScope 0.41.4 Full Application Audit

Release target: VulkanScope 0.41.4 / versionCode 414.

## Scope

This audit rechecks VulkanScope 0.41.3 against PROJECT_RULES, SOURCES, VULKAN_REGISTRY, REFERENCE_PARITY and the accumulated release contracts. The review covers Vulkan evidence semantics, reporting parity, bounded native enumeration, Android lifecycle and Surface ownership, Turnip import safety, update/database networking, Material 3 Expressive usability, package metadata, build-chain hardening and source-package cleanliness.

## Correctness fixes

- Queue-family Vulkan Video evidence no longer serializes the default numeric zero mask into schema-3 technicalReport when the query state is not_applicable, unavailable or unknown. The numeric and U64 fields are null unless the query state is available; query status and reason remain authoritative. A queried zero remains valid and is still named VK_VIDEO_CODEC_OPERATION_NONE_KHR.
- Device-extension enumeration retains the final bounded entries returned with repeated VK_INCOMPLETE as partial positive evidence. The device-extension state remains incomplete, so missing extensions are not inferred unsupported and partial data is not used as proof of complete enumeration.
- Properties & Limits unique-property totals exclude Vulkan Query Safety diagnostics. Safety rows remain in the complete evidence dataset and receive their own unique-diagnostic count.
- Host Image Copy source/destination layout arrays now treat the two pointer/count pairs independently: one oversized list no longer prevents collection of the other bounded list, and post-query counts are validated against the allocated capacities before any returned layout list is reported. This applies to both `VK_EXT_host_image_copy` and promoted Vulkan 1.4 property paths.

## Security and privacy hardening

- VulkanScope Database submission uses a dedicated HTTPS client with both same-scheme and cross-scheme redirect following disabled. The complete report therefore cannot be automatically replayed to a redirect target.
- The fixed official Database hostname/root validation remains mandatory before submission.
- Gradle and Kotlin build caches are explicitly disabled in the checked-in release configuration as defense-in-depth for current Kotlin build-cache deserialization security guidance. This affects the build pipeline, not Vulkan runtime collection.
- Existing APK update provenance, package identity, signature lineage, version monotonicity, bounded download and explicit user-action gates remain unchanged.
- No new runtime endpoint, permission, analytics, hardware identifier or automatic upload is introduced.

## Usability and design consistency

- The selected-format detail dialog is vertically scrollable so decoded/raw VkFormatProperties3 and Image Format Properties2 evidence remains accessible on small displays and constrained Android TV layouts.
- Material 3 Expressive visual identity, VulkanScope dark palette, navigation order, focus behavior and semantic status colors remain unchanged.

## Specification and dependency review

- Published/query Vulkan baseline remains Vulkan 1.4.360 dated 2026-08-14.
- Android compile/target baseline remains API 37, including HDR_TYPE_HLG_PLUS value 6.
- AGP remains 9.3.1 with the Gradle 9.7.x project family; AGP 9.3 requires Gradle 9.5.0 or newer.
- Compose UI/foundation/animation remain 1.12.0 and Material 3 remains 1.5.0-alpha26, matching the current project rules and the AndroidX release baseline reviewed for this release.
- Vulkan-Headers remains pinned to the validated VK_HEADER_VERSION 360 project revision.

## Memory, lifecycle and crash review

Static ownership review found no new unmatched Vulkan instance, Surface, native window, device, shader module, pipeline layout or pipeline ownership path in the audited source. JNI UTF string acquisitions retain matching releases. VulkanProbeService continues to release the Surface parcel and shut down its single worker, and Activity destruction terminates active isolated probe/update work.

This is a static/source audit. A claim of zero runtime leaks, zero driver-triggered crashes or zero device-specific failures requires real-device instrumentation and hostile/buggy-driver testing; those properties are not inferred from static analysis.

## Reporting coverage

UI, TXT, self-contained HTML and Database technicalReport continue to preserve the same canonical evidence classes. The 0.41.4 corrections remove ambiguity without truncating the report or changing submission schema 2 / technicalReport schema 3.

## Validation

- tools/verify_release.py must pass for 0.41.4 / 414.
- Generated Vulkan catalog/reference assets remain pinned and unchanged unless regenerated from the same validated Vulkan 1.4.360 inputs.
- Release ZIP must contain no build/cache directories, Python cache artifacts, temporary source backups or unrelated files.
- A clean `./gradlew :app:assembleRelease --offline --no-daemon` was attempted after the fixes. The wrapper could not start because Gradle 9.7.0 was not cached and `services.gradle.org` was unreachable in the audit environment. This is an environment/dependency-resolution failure, not evidence of either build success or a source compile failure.
- Full Android release compilation remains a separate environment-dependent validation gate and must not be claimed when dependencies/toolchains cannot be resolved.
